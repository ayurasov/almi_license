# Резервное копирование и восстановление (E15-03)

Скрипты `deploy/ops/backup.sh`, `deploy/ops/restore.sh`, `deploy/ops/drill.sh` одинаковы для центрального и локального сервера. Они запускаются в образе `postgres:17`: в нём есть `pg_dump` той же версии, что сервер БД, а также `gpg` и `bash`.

## Что копируется

| Что | Как | Где |
|---|---|---|
| База данных | `pg_dump -Fc`, затем `gpg --symmetric --cipher-algo AES256` с защитой целостности | `$BACKUP_DIR/almi-<время UTC>.dump.gpg` и `.sha256` |
| Ключ локального сервера (`LOCAL_SERVER_KEY_FILE`) | Отдельно, тем же шифрованием, если задан `SERVER_KEY_FILE` | `$BACKUP_DIR/almi-<время>.server-key.gpg` |
| Метка успеха | Время UTC последней удачной копии | `$BACKUP_DIR/last-success` |

Ключ выпуска центрального сервера и корневой ключ скрипт не копирует. Они хранятся по регламенту церемонии ключей (документ 1, раздел 9).

Пароль шифрования передаётся только файлом Docker secret (`BACKUP_PASSPHRASE_FILE`), не аргументом и не переменной. Храните его отдельно от копий: без пароля копии не восстановить.

## Расписание и хранение

Копия снимается раз в сутки. Хранение — 30 дней (`BACKUP_KEEP_DAYS`), более старые файлы удаляются при следующем запуске. Это даёт RPO 24 ч (документ 1, раздел 4). Пример задания cron на хосте:

```
17 2 * * *  docker run --rm --network almi \
  -e DATABASE_URL -e BACKUP_DIR=/backups -e BACKUP_PASSPHRASE_FILE=/run/secrets/backup \
  -v /var/backups/almi:/backups -v /etc/almi/backup-passphrase:/run/secrets/backup:ro \
  -v /opt/almi/ops:/ops:ro postgres:17 /ops/backup.sh
```

`DATABASE_URL` берётся из окружения задания (файл `.env` с правами 0600), в журнал не выводится.

Мониторинг: сервер отдаёт на `/metrics` метрику `almi_backup_age_seconds`, если `BACKUP_STATUS_FILE` указывает на `last-success`. Оповещение — при значении больше 26 ч или −1 (копии нет), раздел 11 документа 7.

## Восстановление

1. Остановите API и обработчик задач (`docker compose stop api worker`).
2. Восстановите копию в базу (скрипт заменяет её содержимое):
   `DATABASE_URL=… BACKUP_PASSPHRASE_FILE=… restore.sh /backups/almi-….dump.gpg`.
   Сначала проверяется сумма SHA-256. Испорченная или неполная копия не восстанавливается.
3. Проверьте журнал аудита и миграции:
   `manage.py verify_audit` и `manage.py migrate --check`.
4. Запустите сервисы и проверьте `/ready`.

Цель восстановления этапа 1 — 4 ч (RTO).

## Учение

`make backup-drill` снимает копию с `DATABASE_URL`, восстанавливает её в `almi_restore_drill` и сравнивает число строк основных таблиц. Затем проверяет цепочку аудита восстановленной базы. Учение идёт в CI на каждом запросе на слияние (задача `backup-drill`). На стендах его проводят раз в квартал на копии продуктивной базы и записывают время восстановления в журнал выпуска.
