# SBOM: состав поставки, зависимости и лицензии

| Параметр | Значение |
|---|---|
| Что описывает | Все артефакты, которые АЛМИ передаёт заказчикам и командам продуктов, и инструменты разработки |
| Формат | CycloneDX 1.6 JSON, один файл на артефакт; отчёт Markdown и CSV; тексты лицензий (notices) |
| Как собрать | `make sbom VERSION=<версия>` локально; задача CI `sbom` на каждый запрос на слияние (артефакт `sbom`) |
| Инструменты | Syft 1.54.1 (образы и lock-файлы, документ 1, раздел 13); `tools/sbom/sbom.py` (vcpkg, вложенные библиотеки, политика, отчёт; только стандартная библиотека Python) |
| Политика лицензий | `tools/sbom/license-policy.json`; изменение — решение руководителя проекта (`docs/decisions.md`) |

## 1. Что входит в SBOM

| Файл | Артефакт поставки | Кому передаётся | Что перечислено |
|---|---|---|---|
| `almi-license.cdx.json` | Образ сервера `almi-license:<версия>` | Центральный сервер; заказчики — в комплекте локального сервера | Пакеты Debian базового образа `python:3.13-slim`, интерпретатор Python, пакеты Python из `server/uv.lock` (прямые и транзитивные), библиотеки внутри колёс Python |
| `almi-license-console.cdx.json` | Образ консоли `almi-license-console:<версия>` | То же | Пакеты Debian образа `nginx:1.27`; пакеты npm, которые входят в сборку консоли (зависимости выполнения из `console/package-lock.json`) |
| `dl/license_module-x64-linux.cdx.json`, `dl/license_module-x64-windows-static.cdx.json` | Модуль DL `liblicense_module.so`, `license_module.dll` | Команды продуктов АЛМИ и партнёров: модуль встраивается в их продукты | Библиотеки vcpkg, статически связанные с модулем: libsodium, curl, OpenSSL (Linux; на Windows — Schannel ОС), zlib, nlohmann/json |
| `almi-keytool.cdx.json` | Инструмент церемонии ключей | Офлайн-рабочее место ключевой церемонии | Пакеты Python из `tools/almi-keytool/uv.lock`, libsodium внутри PyNaCl |
| `postgres.cdx.json`, `nginx.cdx.json` | Образы `postgres:17`, `nginx:1.27` без изменений | Заказчики — в комплекте локального сервера | Пакеты Debian, утилиты Go образа PostgreSQL (`gosu`) |
| `almi-license-dev.cdx.json` | — (в поставку не входит) | — | Разработка, тесты и CI: группа `dev` сервера, `devDependencies` консоли, тестовые порты vcpkg (GoogleTest, cpp-httplib, Brotli) — только то, чего нет в поставке |
| `sbom-report.md`, `sbom-components.csv` | — | Юристы, ТЛ, руководитель проекта | Сводка, лицензии, вердикты политики, полный перечень |
| `notices/*.txt` | — | Вместе с артефактом | Тексты лицензий и уведомления об авторских правах сторонних компонентов (раздел 5) |
| `SHA256SUMS` | — | — | Суммы всех файлов каталога |

Каждый компонент в SBOM несёт:
- имя, версию и `purl`;
- лицензию — идентификатор или выражение SPDX, для пакетов Debian — имена из файла copyright;
- свойство `almi:policy-kind` — как компонент поставляется (раздел 4).

У пакетов Syft есть ещё CPE и пути в образе. У библиотек vcpkg — свойства порта, ссылки на исходники и признак статического связывания. У библиотек внутри колёс — пакет-носитель (`almi:vendored-in`).

Метка времени SBOM — время коммита. Номер (`serialNumber`) выводится из содержимого: повторная сборка того же коммита в том же окружении даёт те же файлы.

## 2. Как собрать

### 2.1. Локально или на машине выпуска

```sh
make sbom VERSION=1.0.0           # результат в dist/sbom
```

Нужно:
- Docker с образами `almi-license:<VERSION>`, `almi-license-console:<VERSION>`, `postgres:17`, `nginx:1.27`. Их собирает `make bundle-airgap`, или соберите вручную, как в `tools/build_airgap_bundle.sh`;
- `uv`;
- `console/node_modules` (`npm ci --prefix console`);
- Syft. `tools/sbom/install-syft.sh` скачивает закреплённую версию и проверяет SHA-256; можно указать свой бинарный файл в `SYFT=…`.

SBOM модуля DL строится из дерева vcpkg сборки модуля:
- `VCPKG_INSTALLED=sdk/cpp/build/vcpkg_installed VCPKG_TRIPLET=x64-linux make sbom VERSION=…`;
- либо положите в `dist/sbom/dl/` и `dist/sbom/notices/` файлы из артефактов CI `license_module-*` (каталог `build/sbom/`).

`PARTS` ограничивает прогон, например `PARTS="images keytool"`. Отчёт строится всегда, по всем SBOM каталога.

Код возврата 1, если:
- компонент нарушает политику лицензий;
- в колесе Python появилась библиотека, не описанная в `tools/sbom/vendored.json`, или изменилась версия описанного колеса.

### 2.2. В CI

Задача `test-dl` (Linux и Windows) после сборки модуля:
- пишет его SBOM и notices в артефакт `license_module-<ОС>` (`build/sbom/`);
- проверяет SBOM по политике.

Задача `sbom` (после `test-dl`):
1. Собирает образы этого коммита.
2. Берёт SBOM модуля обеих платформ.
3. Выполняет `tools/sbom/build.sh`.
4. Публикует артефакт `sbom`, а сводку — в итог задачи.

Нарушение политики делает CI красным.

### 2.3. В выпуске

Порядок выпуска (документ 7) дополняется шагом:
1. `make sbom VERSION=<версия>` на тех же образах, что уходят в комплект.
2. `SBOM_DIR=dist/sbom make bundle-airgap VERSION=<версия> …`: комплект локального сервера получает каталог `sbom/`. Скрипт проверяет, что SBOM сделан для той же версии.
3. Команды продуктов получают SBOM и notices модуля вместе с модулем (артефакт `license_module-*`, `docs/integration/product-guide.md`, раздел 1).

## 3. Откуда берутся данные

| Источник | Чем читается | Что даёт |
|---|---|---|
| Образы (`docker:<образ>`) | Syft | Пакеты Debian (`dpkg`) с лицензиями из `/usr/share/doc/*/copyright`, пакеты Python из `/opt/venv` с лицензиями из метаданных, бинарные файлы известных программ |
| `console/package-lock.json` | Syft | Пакеты npm сборки и поле `license` каждого |
| Окружения `uv sync --frozen` (keytool; сервер с группой `dev`) | Syft | Пакеты Python ровно по `uv.lock` |
| `vcpkg_installed/vcpkg/status`, `…/share/<порт>/vcpkg.spdx.json`, `…/copyright` | `sbom.py vcpkg` | Порты и их зависимости, версии, лицензии (SPDX порта), источники, тексты copyright. Модуль получает замыкание зависимостей libsodium, curl и nlohmann-json; остальные порты, кроме служебных `vcpkg-*`, уходят в SBOM разработки |
| `tools/sbom/vendored.json` | `sbom.py finalize` | Библиотеки внутри колёс, которых Syft не видит (раздел 3.1) |
| `overrides` в политике | `sbom.py finalize` | Установленная лицензия там, где метаданные пакета её не дают или дают не в виде SPDX (раздел 3.2) |

### 3.1. Библиотеки внутри колёс Python

Колёса manylinux несут свои копии системных библиотек:
- `psycopg-binary` — libpq, OpenSSL, MIT Kerberos, OpenLDAP, Cyrus SASL, libxcrypt, keyutils и другие в каталоге `psycopg_binary.libs/`;
- `pillow` — FreeType, HarfBuzz, libjpeg-turbo, libpng, LibTIFF, libwebp и другие в `pillow.libs/`;
- статически связанные: OpenSSL в `cryptography`, libffi в `cffi`, Argon2 в `argon2-cffi-bindings`, LibYAML в `pyyaml`, libsodium в `pynacl`.

Syft перечисляет только сами пакеты. `vendored.json` описывает вложенные библиотеки: имя, версию (где библиотека её сообщает), лицензию, файлы.

`finalize` сверяет описание с образом: каждый файл `*.libs/*` должен быть описан, а версия колеса — совпадать с записанной. При обновлении `uv.lock` проверка падает, пока запись не обновлена. Так новая вложенная библиотека не пройдёт незамеченной.

### 3.2. Установленные лицензии (`overrides`)

Лицензия устанавливается вручную, когда метаданные пакета не дают ответа:
- у пакета нет лицензии в метаданных (`sqlparse`) или она записана текстом («Dual License» у `python-dateutil`);
- Syft не разобрал файл copyright Debian и записал хэш текста (`libc6`, `libgcc-s1`, `libgnutls30` и др.);
- у программ Go в образе PostgreSQL нет сведений о лицензии.

Для каждой записи указан источник: файл copyright в образе или файл LICENSE пакета. Лицензии пакетов Debian установлены по их файлам `/usr/share/doc/<пакет>/copyright`. Для библиотек выбрана лицензия самой библиотеки, а не утилит того же исходного пакета: например, `libgnutls30` — LGPL-2.1-or-later, а GPL относится к утилитам GnuTLS.

## 4. Политика лицензий

### 4.1. Категории

| Категория | Примеры | Смысл |
|---|---|---|
| Разрешительная | MIT, BSD-*, Apache-2.0, ISC, Zlib, curl, PostgreSQL, PSF-2.0, CC0-1.0, OLDAP-2.8 | Сохранять уведомление об авторских правах и текст лицензии |
| Слабый копилефт | LGPL-*, MPL-2.0, GPL с исключением о связывании (GCC runtime, Bison, Classpath) | Изменения самой библиотеки открываются; использование без изменений и динамическое связывание допустимы |
| Сильный копилефт | GPL-*, GFDL-* | Производное произведение распространяется по той же лицензии |
| Сетевой копилефт | AGPL-*, SSPL-*, OSL-* | То же, и при предоставлении по сети |
| Не открытая | BUSL-*, Elastic-*, Commons Clause, CC-BY-NC-* | Ограничения на коммерческое использование |
| Не определена | Нет лицензии, нераспознанное имя | Нужно установить лицензию |

Выражения SPDX:
- `A OR B` — по более свободной ветви;
- `A AND B` — по более строгой;
- несколько лицензий одного пакета действуют вместе (как `AND`).

### 4.2. Как поставляется компонент (`almi:policy-kind`)

| Вид | Что это | Правило |
|---|---|---|
| `linked` | Модуль DL: компилируется в продукты АЛМИ и партнёров, статически | Только разрешительные; всё остальное — нарушение |
| `application` | Наше приложение как оно поставляется: пакеты Python образов и keytool, пакеты npm сборки консоли, библиотеки внутри колёс | Разрешительные; слабый копилефт — с обязательствами; сильный, сетевой, не открытые и неопределённые — нарушение |
| `os` | Всё, что Syft находит в образе помимо наших экосистем: пакеты Debian, бинарные файлы, jar базового образа; сторонние образы целиком | Отдельные программы, с нашим кодом не связываются: копилефт — с обязательствами; сетевой, не открытые, неопределённые — проверить. Категорию дают распознанные лицензии пакета: Debian перечисляет в copyright и собственные имена уведомлений отдельных файлов |
| `dev` | Инструменты разработки, тестов и CI | Не поставляются: всё допустимо; сетевой копилефт, не открытые и неопределённые — проверить |

### 4.3. Вердикты и обязательства

| Вердикт | Что делать |
|---|---|
| Допустимо | Сохранять notices |
| Допустимо с обязательствами | Выполнить обязательство категории (ниже); отчёт перечисляет такие компоненты в разделе 5 |
| Проверить | Установить лицензию (`overrides`) или принять решение; CI не останавливается |
| Нарушение | Убрать компонент или заменить; изменить политику может только руководитель проекта. CI красный |

Обязательства:
- **Слабый копилефт в приложении.** Сейчас это psycopg, psycopg-binary и psycopg-pool (LGPL-3.0-only), а также keyutils и libxcrypt внутри psycopg-binary (LGPL-2.1-or-later):
  - библиотеки используются без изменений и загружаются динамически: Python импортирует модуль, разделяемые библиотеки загружаются из `psycopg_binary.libs`;
  - тексты лицензий — в `notices/almi-license-python.txt`;
  - исходный код той же версии предоставляется по запросу получателя комплекта — это PyPI и проекты, указанные в SBOM;
  - пользователь может заменить библиотеку: образ не запрещает этого технически.
- **Копилефт пакетов ОС.** Пакеты Debian базовых образов передаются без изменений. Исходные тексты доступны в архиве Debian (`snapshot.debian.org`) по версии из SBOM. Тексты лицензий лежат в самих образах: `/usr/share/doc/<пакет>/copyright`.

## 5. Тексты лицензий (notices)

| Файл | Для чего | Откуда |
|---|---|---|
| `notices/license_module-<платформа>.txt` | Кладётся в дистрибутив продукта рядом с модулем DL | Файлы `copyright` портов vcpkg |
| `notices/almi-license-python.txt` | Пакеты Python образа сервера | Файлы `LICENSE*`, `COPYING*`, `NOTICE*`, `AUTHORS*` из `*.dist-info` в образе |
| `notices/almi-license-console-npm.txt` | Пакеты npm сборки консоли | Файлы `LICENSE*` в `node_modules` |
| `notices/almi-keytool-python.txt` | Пакеты Python almi-keytool | То же, из окружения keytool |

У пакетов ОС тексты лицензий остаются в образах (`/usr/share/doc`). Если пакет npm не приложил файл лицензии, notices отмечают это. Лицензию такого пакета указывают его метаданные и SBOM.

Выводы:
1. **Нарушений нет.**
2. **Модуль DL** связан только с библиотеками под разрешительными лицензиями:
   - Linux: libsodium 1.0.22 (ISC), curl 8.23.0 (curl AND ISC AND BSD-3-Clause), OpenSSL 3.6.5 (Apache-2.0), zlib 1.3.2 (Zlib), nlohmann/json 3.12.0 (MIT);

5. **Разработка.** Сильный копилефт есть только среди инструментов, которые не поставляются.

## 7. Ограничения

- **Инструменты CI** (действия GitHub, gitleaks, uv, clang-format, Syft) в SBOM не входят: они не попадают ни в один артефакт. Их перечень и версии — в `docs/dependencies.md`.
- **Системные библиотеки машины пользователя** не входят в SBOM модуля DL. Модуль загружает их динамически, и в дистрибутив они не входят: `libstdc++`, `libc` на Linux, CRT и Schannel на Windows.
- **Пакеты npm** берутся из lock-файла по зависимостям выполнения. Часть из них используется только при сборке и в итоговый бандл не попадает — например, `@babel/parser` из `@vue/compiler-sfc`. Перечень поэтому шире фактического, то есть осторожнее.
- **Версии части вложенных библиотек** неизвестны: библиотека не сообщает версию, известен только soname. Например, Kerberos в psycopg-binary и libsodium в PyNaCl. Поле версии у них пустое.
- **Уязвимости** не проверяются. По спецификации (документ 1, раздел 13; документ 7, раздел 6) сканирование образов (Trivy) и подпись образов (cosign) — этап 2. SBOM CycloneDX подходит для них без доработки.
- **SBOM не подписан.** Целостность каталога проверяется по `SHA256SUMS`, а сам файл сумм в комплекте локального сервера покрыт общим `SHA256SUMS` комплекта.
