## 1. Назначение

Документ — рабочий сценарий выполнения этапа 1 силами разработчиков с ИИ-ассистентами. Он содержит:

- порядок итерационной разработки: что делается в каждой итерации, в какой последовательности и как проверяется;
- шаблоны промптов для каждого шага работы над историей;
- готовые промпты для ключевых историй бэклога (документ 3) по всем потокам: сервер, консоль, модуль DL, тестирование, DevOps;
- контрольные промпты для завершения итерации и этапа.

Промпты рассчитаны на агентов, работающих в репозитории (Cursor, Claude Code, Copilot Workspace и аналогичные), и на чат-модели для ревью. Текст промптов — на русском; имена в коде, коммитах и API — на английском.

## 2. Итерационная модель

### 2.1. Уровни

| Уровень | Длительность | Результат | Проверка |
|---|---|---|---|
| Этап | 6 недель | Выпуск системы лицензирования | Readiness gate (раздел 15.7 документа 1) |
| Итерация | 1 неделя (I1–I6) + подготовка I0 | Работающий прирост на стенде `test-central` | Демонстрация и контрольный промпт итерации |
| История | 0,25–2 дня | Слитый запрос в `stage1` | Критерии приёмки, CI, ревью |
| Шаг | 30–120 минут | Коммит | Тесты шага зелёные |

Правило: каждая итерация заканчивается работающей системой. Ничего не копится «до интеграции в конце» — на стенде всегда последняя слитая версия, и сквозной сценарий прошлой итерации продолжает проходить.

### 2.2. Цикл истории

```
P0 старт сессии → P1 план → P2 тесты (красные) → P3 реализация (зелёные)
   → P4 самопроверка → P5 исправление CI → P6 независимое ревью
   → [P7 ревью критичного модуля] → P8 документация → P9 закрытие
```

| Шаг | Кто | Что получается | Коммит |
|---|---|---|---|
| P0 | Разработчик → ассистент | Ассистент загрузил контекст и подтвердил понимание | — |
| P1 | Ассистент, утверждает разработчик | План: файлы, тесты, риски, вопросы | — |
| P2 | Ассистент | Тесты по критериям приёмки; падают | `test(<модуль>): … (Exx-yy)` |
| P3 | Ассистент | Минимальная реализация; тесты проходят | `feat(<модуль>): … (Exx-yy)` |
| P4 | Ассистент | Отчёт о соответствии критериям и правилам `AGENTS.md` | при необходимости `refactor` |
| P5 | Ассистент | Зелёный CI | `fix(…)` |
| P6 | Другая сессия ассистента | Список замечаний | — |
| P7 | Технический лидер с ассистентом | Чек-лист раздела 8 документа 6 | — |
| P8 | Ассистент | Документация, `CHANGELOG.md` | `docs(…)` |
| P9 | Ассистент | Запись в журнале прогресса, описание запроса на слияние | — |

### 2.3. Правила сессий

1. **Одна история — одна ветка — одна сессия.** Новая история начинается в новой сессии с промпта P0. Длинные сессии теряют контекст и начинают противоречить ранним решениям.
2. **Новая сессия при переполнении.** Если ассистент начал забывать ограничения, повторять исправленные ошибки или контекст занят больше чем на 70 %, сессия закрывается промптом P9 (частичное закрытие) и продолжается новой с P0.
3. **Реализация и ревью — разные сессии.** Сессия, которая писала код, не делает его независимое ревью (P6).
4. **Разработчик утверждает план.** Ассистент не пишет код, пока разработчик не ответил «план утверждён» на P1.
5. **Остановка при неясности.** Если контракт неясен или противоречив, ассистент останавливается и формулирует вопрос (P12). Ответ фиксируется в ADR или в журнале решений, а не только в чате.
6. **Коммит на каждый зелёный шаг.** Не накапливать несколько шагов в одном коммите; порционные коммиты в ветку задачи, squash при слиянии в `stage1`.
7. **Контракты неприкосновенны.** Изменение `contracts/` — только отдельной историей с меткой `contract` и ревью технического лидера.

### 2.4. Память проекта в репозитории

Ассистент не помнит прошлых сессий. Память хранится в файлах, которые он читает в P0:

| Файл | Содержимое | Кто обновляет |
|---|---|---|
| `AGENTS.md` | Правила и команды (документ 6, раздел 3) | Технический лидер |
| `docs/progress/stage1.md` | Журнал: закрытые истории, текущая итерация, открытые вопросы | Ассистент в P9, разработчик проверяет |
| `docs/progress/iteration-N.md` | План и итог итерации N | Технический лидер в начале и конце итерации |
| `docs/decisions.md` | Мелкие решения, принятые в историях (что не тянет на ADR) | Ассистент в P9 |
| `docs/adr/` | Архитектурные решения | Технический лидер |
| `docs/specs/` | Документы 1–9 комплекта в Markdown | Технический лидер |

Документы комплекта кладутся в `docs/specs/` в начале I0 с короткими именами: `01-architecture.md`, `02-interaction-spec.md`, `03-backlog.md`, `04-catalog.md`, `05-messages.md`, `06-ai-rules.md`, `07-environments.md`, `08-lk-tz.md`. Контракт Product API лежит в `contracts/openapi-product-api-v1.yaml`. Промпты ниже ссылаются на эти пути.

## 3. Базовые промпты

Шаблоны применяются к любой истории. В угловых скобках — подстановки.

### P0. Старт сессии

```text
Ты работаешь в репозитории almi-license. Мы выполняем историю <ID> «<название>» из docs/specs/03-backlog.md.

Прочитай и держи в контексте:
1. AGENTS.md — правила обязательны.
2. docs/progress/stage1.md — что уже сделано и открытые вопросы.
3. docs/progress/iteration-<N>.md — план текущей итерации.
4. Строку истории <ID> в docs/specs/03-backlog.md.
5. Разделы: <docs/specs/0X-….md, разделы …>.
6. Контракт: <contracts/… , operationId / схема / векторы>.
7. Существующий код модулей: <пути>.

Не пиши код. Ответь:
- в 5–7 пунктах, что требуется сделать и как это проверяется;
- какие правила AGENTS.md здесь особенно важны;
- какие файлы ты будешь менять и какие менять нельзя;
- что неясно или противоречит контракту (если ничего — так и напиши).
```

### P1. План истории

```text
Составь план реализации истории <ID>. Пока без кода.

Формат:
1. Тесты: список тест-кейсов, по одному на каждый критерий приёмки и на каждый код ошибки; пути файлов тестов.
2. Изменения: файлы и что в каждом меняется; новые функции и их сигнатуры.
3. Шаги: 3–6 шагов, каждый заканчивается зелёными тестами и коммитом; сообщение коммита для каждого.
4. Риски: где можно нарушить правила AGENTS.md (транзакции, время, секреты, модульные границы).
5. Вопросы, без ответа на которые нельзя начинать.

Объём изменения — до 400 строк без тестов. Если больше — предложи разбить историю на части.
```

После ответа разработчик пишет: `План утверждён` или правки к плану.

### P2. Тесты

```text
Выполни шаг 1 плана: напиши тесты для истории <ID>.

Требования:
- по одному тесту на каждый критерий приёмки и каждый код ошибки из плана;
- данные — через фабрики и фикстуры, без сети и без системного времени (FrozenClock);
- для правил с границами — property-тесты hypothesis;
- эталонные векторы из contracts/vectors используются напрямую, без копирования значений в тест.

Реализацию не пиши. Запусти тесты и покажи, что они падают по ожидаемой причине (нет функции / неверный ответ), а не из-за ошибок в самих тестах.
Сделай коммит: test(<модуль>): <кратко> (<ID>).
```

### P3. Реализация

```text
Выполни шаги <2–…> плана: реализуй минимальный код, который проходит тесты <ID>.

Ограничения:
- бизнес-логика только в server/apps/<модуль>/domain/;
- время только через Clock, криптография только через CryptoProvider;
- изменения прав — в transaction.atomic с select_for_update на лицензии;
- событие аудита на каждое изменение прав;
- ошибки — доменные исключения, отображение в problem+json в api_product/errors.py.

После каждого шага: make lint и тесты затронутого модуля; коммит с сообщением из плана.
Не трогай файлы вне плана. Если без этого не обойтись — остановись и объясни почему.
```

### P4. Самопроверка

```text
Проверь свою реализацию <ID> и ответь таблицей:
| Критерий приёмки | Где реализован | Какой тест проверяет | Выполнен |

Затем пройди по пунктам 1–15 «Жёстких правил» AGENTS.md и для каждого: не применимо / соблюдено (где) / нарушено (где).

Затем:
- найди в изменениях: datetime.now, time.time, print, закомментированный код, TODO без номера истории, секреты, широкие except;
- проверь, что журналы не содержат ключей, аренд, подписей, хэшей отпечатка;
- проверь, что новые поля API есть в contracts/ (make contract-check).
Исправь найденное отдельным коммитом refactor(<модуль>): self-review fixes (<ID>).
```

### P5. Исправление CI

```text
CI упал на задаче <имя задачи>. Вот журнал:
<вставить фрагмент журнала>

Найди первопричину, а не симптом. Запрещено: отключать проверки, снижать пороги покрытия, добавлять # noqa / # type: ignore / eslint-disable без объяснения в комментарии со ссылкой на историю, менять тесты так, чтобы они проверяли меньше.
Опиши причину в одном абзаце, исправь, запусти ту же проверку локально, сделай коммит fix(<модуль>): <причина> (<ID>).
```

### P6. Независимое ревью

Выполняется в новой сессии (или другой моделью) над diff запроса на слияние.

```text
Ты — ревьюер. Тебе дан diff запроса на слияние по истории <ID> репозитория almi-license.
Правила проекта — AGENTS.md (приложен). Критерии приёмки истории — <вставить>.
Контракт — <фрагмент OpenAPI / схемы>.

Найди:
1. Невыполненные или частично выполненные критерии.
2. Расхождения с контрактом: поля, типы, коды ошибок, заголовки.
3. Нарушения правил AGENTS.md.
4. Ошибки конкурентности и транзакций, пограничные случаи дат и null.
5. Уязвимости: инъекции, утечки данных в журналы и ответы, отсутствие проверок размера и прав.
6. Тесты, которые ничего не проверяют или проверяют реализацию, а не поведение.

Формат ответа — таблица: | Важность (блокирует / желательно) | Файл:строка | Проблема | Как исправить |.
Не хвали код и не пересказывай diff. Если замечаний нет — напиши «Замечаний нет» и перечисли, что именно проверил.
```

### P7. Ревью критичного модуля

Технический лидер использует вместе с чек-листом раздела 8 документа 6.

```text
Проверь diff модуля <signing / crypto / activation / policy / packages / audit / iam / compat / DL: …> по чек-листу:
<вставить строку чек-листа из раздела 8 документа 6 для этой области>

Для каждого пункта чек-листа: соблюдено / нарушено / не проверить по diff (что нужно посмотреть дополнительно).
Отдельно:
- построй сценарий атаки или гонки, который мог бы сломать этот код, и укажи, какой тест его закрывает; если теста нет — предложи тест;
- проверь сравнения секретов на постоянное время, порядок «проверка подписи → разбор полезной нагрузки», ограничение размера до разбора.
```

### P8. Документация

```text
Обнови документацию по истории <ID>:
- CHANGELOG.md: раздел Unreleased, одна строка на изменение поведения;
- docs/<руководство>: если меняется работа оператора, администратора или продукта;
- docstring доменных функций: что делает, исключения, инварианты.
Не переписывай документы целиком и не меняй docs/specs/. Коммит docs(<модуль>): <кратко> (<ID>).
```

### P9. Закрытие истории

```text
История <ID> готова к слиянию. Сделай:
1. Добавь в docs/progress/stage1.md запись:
   - <ID> — <название> — закрыта <дата>; что сделано (2–3 пункта); ограничения и известные упрощения; что разблокировано для других историй.
2. Если в истории принимались решения, не описанные в docs/specs, — добавь их в docs/decisions.md (дата, история, решение, причина).
3. Сформируй описание запроса на слияние по шаблону раздела 11 документа 6.
4. Перечисли открытые вопросы для технического лидера (если есть).
```

Частичное закрытие (при смене сессии): тот же промпт с заменой п. 1 на «что сделано, что осталось, на каком шаге плана остановились, какие тесты красные».

### P10. Завершение итерации

Выполняет технический лидер в чате с приложенными `docs/progress/stage1.md`, `docs/progress/iteration-N.md`, отчётом CI и протоколом демонстрации.

```text
Итерация <N> завершена. Проанализируй приложенные материалы и ответь:
1. Какие истории плана итерации закрыты, какие нет и почему.
2. Выполнены ли критерии выхода итерации (из раздела <N> документа 10).
3. Какие решения из docs/decisions.md нужно поднять до ADR или отразить в docs/specs.
4. Где накоплен технический долг (упрощения, TODO, пропущенные тесты) и в какую итерацию его включить.
5. Как перенос незакрытых историй влияет на критический путь (раздел 6 документа 3).
6. Предложи план итерации <N+1>: истории по потокам, порядок, риски.
Сформируй текст docs/progress/iteration-<N>.md (итог) и docs/progress/iteration-<N+1>.md (план).
```

### P11. Разбор дефекта

```text
Дефект: <описание, шаги воспроизведения, ожидаемое и фактическое поведение, журнал, request_id>.
1. Напиши тест, который воспроизводит дефект и падает. Коммит test(<модуль>): reproduce <номер дефекта>.
2. Найди первопричину; объясни, почему существующие тесты её не поймали.
3. Исправь минимально. Коммит fix(<модуль>): <причина> (<номер дефекта>).
4. Предложи, какие ещё места могут иметь ту же ошибку, и проверь их.
```

### P12. Неясность или тупик

```text
Остановись. Сформулируй вопрос для технического лидера:
- что именно неясно или противоречит (цитата из docs/specs или contracts с указанием раздела);
- 2–3 варианта решения с последствиями для контракта, продуктов и тестов;
- какой вариант ты предлагаешь и почему.
До ответа не продолжай реализацию этой части. Если возможно, продолжи независимые шаги плана.
```

Если ассистент трижды не может исправить одну и ту же ошибку, разработчик прекращает попытки, откатывает ветку к последнему зелёному коммиту и решает задачу вручную или разбивает её на меньшие шаги.

## 4. Как пользоваться промптами итераций

Для каждой итерации ниже указаны цель, входные условия, план по потокам, готовые промпты для ключевых историй, демонстрационный сценарий и критерии выхода. Готовый промпт итерации заменяет шаги P0–P1 базового цикла: в нём уже есть контекст и план. Шаги P2–P9 выполняются как обычно.

Истории без готового промпта выполняются по шаблону P0 с подстановкой строки из бэклога: она содержит критерии приёмки, исполнителя и ссылки на разделы.

Порядок внутри итерации: сначала истории критического пути (раздел 6 документа 3), затем остальные. В каждом потоке одновременно в работе не больше двух историй.

## 5. Итерация I0. Подготовка (дни 1–2 недели 1)

**Цель.** Пустой, но полностью рабочий репозиторий: структура, правила, локальное окружение, CI, в котором проходит тривиальный тест на каждом языке.

**Входные условия.** Документы 1–9 утверждены или переданы на утверждение; создан репозиторий; есть раннеры CI.

| Поток | Истории |
|---|---|
| TL | E00-05 (`AGENTS.md`, структура), размещение `docs/specs/` |
| DO | E00-06 (CI), E00-07 (локальное окружение) |
| FS1 | Каркас Django-проекта, `infra/clock`, `infra/crypto` (интерфейсы) |
| CPP | E13-01 (каркас CMake) |
| QA | E00-09 (запись реальных запросов Nextcloud и `registration.sh`) |

### I0-01. Структура репозитория

```text
Создай структуру репозитория almi-license по разделу 14 docs/specs/01-architecture.md.

Сделай:
1. Каталоги: contracts/{schemas,vectors}, server/{almi_license,apps,infra,tests}, console, sdk/{cpp,php}, tools/{almi-keytool,conformance}, deploy/{central,local,dev,airgap-bundle}, docs/{adr,progress,specs}.

- LM_Initialize при старте до создания главного окна; LM_Shutdown при выходе; колбэк изменения состояния обновляет интерфейс в UI-потоке;
- доступность функций — только LM_HasFeature("<функция>") из каталога docs/specs/04-catalog.md раздел 5.1; кэшировать результат не дольше чем до следующего колбэка;
- тексты — из LM_GetMessages; если пусто — встроенные ресурсы с ID из docs/specs/05-messages.md;
- ошибка модуля не должна ронять продукт: любое LM_ERR_* кроме ожидаемых → работа как в UNLICENSED с записью в журнал продукта.

E14-02: диалог активации — элементы и тексты раздела 4.1 документа 5; адрес сервера из настройки.
E14-03: баннер и модальные сообщения по placement и repeat; окно «О программе» — раздел 7 документа 5.
E14-04: неактивные элементы для функций, которых нет в LM_HasFeature, с подсказкой restricted.feature; режим read_only — открытие, печать, экспорт без сохранения.
Для проверки используй заглушку библиотеки (E13-11) с переключением состояний через переменную окружения LM_STUB_STATE.
```

**Демонстрация I4.** Тестовый экземпляр АльтерОфис Web получает срок и лимит пользователей с `test-central`; узел АльтерОС регистрируется старым `registration.sh`; автоосвобождение срабатывает при сдвиге времени стенда; администратор заказчика видит только свои лицензии; тестовая сборка Desktop показывает состояния с заглушкой.

## 13. Признаки проблем и реакция

| Признак | Что означает | Реакция |
|---|---|---|
| Ассистент меняет тесты, чтобы они прошли | Подгонка под реализацию | Откатить; повторить P3 с явным запретом менять тесты |
