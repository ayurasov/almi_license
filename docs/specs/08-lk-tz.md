## 1. Общие сведения

| Параметр | Значение |
|---|---|
| Наименование | Личный кабинет АльтерСофт 3.0 (далее — ЛК 3.0) |

| Основание | Переход на целевую архитектуру лицензирования; прекращение поддержки MariaDB 10.0; устранение ограничений ЛК 2.0 |
| Срок | 13 недель, параллельно этапу 2 системы лицензирования; переключение — до конца инкремента 2 этапа 2 |

## 2. Назначение и цели

ЛК 3.0 — система коммерческого учёта лицензий АльтерСофт: заказчики, их пользователи, выпуск лицензий по артикулам, сертификаты, доступ клиентов к своим лицензиям и техподдержке.

Цели:

1. Перенести ЛК на поддерживаемый стек, единый с системой лицензирования: Django 5.2 LTS, PostgreSQL 17, Vue 3.
2. Разделить ответственность: ЛК ведёт коммерческие данные, система лицензирования — активации, учёт мест и контроль сроков. Активация продуктов из ЛК уходит.
3. Устранить ограничения ЛК 2.0 по безопасности: хранение токенов в `localStorage`, устаревший алгоритм паролей, жёстко заданный список администраторов, локальный кэш для ограничения частоты.
4. Показать клиенту реальные остатки и сроки, получаемые от системы лицензирования.
5. Перенести все данные ЛК 2.0 без потерь и без повторной выдачи ключей.

## 3. Текущее состояние

### 3.1. Функции ЛК 2.0

| Область | Функции |
|---|---|
| Кабинет клиента | Вход, сброс пароля кодом на почту, список лицензий с фильтрами, разбор серийного номера, сертификаты PDF (лицензия, техподдержка) |
| Публичная активация | `/api/activate/` и страница `/activate`: привязка ПК (`data` — MD5, `host`, `lic`), учёт `Used/Total` |
| Генерация лицензий | Мастер артикула (`AA…II`), проверка артикула, дневная квота серийных номеров, поиск клиента по ИНН, выпуск один-к-одному и пакетом, правила ФСТЭК, выгрузка XLSX и письмо отгрузки |
| Пользователи | Создание учётных записей клиента, письмо доступа, повторная отправка, сброс пароля |
| Архив | Предпросмотр и архивирование истёкших лицензий |
| Почта | Журнал исходящих писем |

### 3.2. Ограничения ЛК 2.0

| Ограничение | Последствие |
|---|---|
| MariaDB 10.0.31, не поддерживается производителем; Django 4.2 требует 10.4+, используется доработанный драйвер | Нельзя обновлять Django; риски безопасности и потери данных |
| Схема БД legacy (`Clients`, `Cabinet`, `RegData`, `Licensing`) не управляется миграциями | Любое изменение — ручная работа без истории |
| Пароли: двойной SHA-512 с фиксированной солью | Не соответствует современным требованиям |
| JWT в `localStorage` | Уязвимость к XSS |
| Администраторы задаются списком `ADMIN_ALLOWED_CLIENT_CODES = [6]` | Нет ролей и разграничения прав |
| Ограничение частоты в локальном кэше процесса | Не работает при нескольких процессах |
| Активация и учёт мест внутри ЛК | Дублирует систему лицензирования, нет офлайн-режима, нет контроля сроков |
| Сертификаты через LibreOffice в контейнере приложения | Тяжёлый образ, блокирующие вызовы |

## 4. Границы системы

### 4.1. Распределение ответственности

| Функция | ЛК 3.0 | Система лицензирования |
|---|---|---|
| Заказчики, контакты, пользователи кабинета | Ведёт | Получает минимум: внешний ID, наименование, ИНН |
| Каталог артикулов | Ведёт | Хранит соответствие артикула продукту (документ 4) |
| Выпуск лицензий: серийный номер, код, срок, количество | Ведёт, передаёт через Integration API | Принимает, выдаёт права |
| Продление, отзыв | Инициирует | Исполняет, выпускает новые аренды |
| Активация продуктов, учёт мест, автоосвобождение | — | Ведёт |
| Офлайн-активация, локальные серверы | — | Ведёт |
| Остатки и активность для клиента | Показывает | Отдаёт через Integration API и вебхуки |
| Сертификаты PDF | Формирует | — |
| Письма клиентам о доступе и отгрузке | Отправляет | Письма о сроках — этап 2 системы лицензирования |
| Публичный адрес `/api/activate/` | Перенаправляет на систему лицензирования | Обслуживает адаптером |

### 4.2. Контекст

ЛК 3.0 взаимодействует с:

| Система | Направление | Способ |
|---|---|---|
| Система лицензирования | ЛК → сервер | Integration API (документ 2, раздел 14.2), HMAC, `Idempotency-Key` |
| Система лицензирования | Сервер → ЛК | Вебхуки (документ 2, раздел 14.3) |
| Почтовый сервер | ЛК → SMTP | SMTP с TLS |
| Сервис документов | ЛК → сервис | HTTP внутри контура (Gotenberg или собственный контейнер LibreOffice) |
| Браузер клиента и сотрудника | ↔ | HTTPS |

## 5. Роли

| Роль | Кто | Права |
|---|---|---|
| `client_user` | Пользователь заказчика | Свои лицензии, сертификаты, остатки, смена пароля |
| `client_admin` | Ответственный заказчика | То же + управление пользователями своей организации |
| `sales` | Менеджер продаж | Выпуск лицензий, заказчики, пользователи, письма |
| `support` | Поддержка | Просмотр заказчиков и лицензий, сброс паролей, повторная отправка доступа |
| `license_admin` | Администратор лицензий | Всё по лицензиям, архив, каталог артикулов, продление и отзыв |
| `system_admin` | Администратор ЛК | Пользователи сотрудников, роли, настройки, журнал аудита, интеграции |

Сотрудники и пользователи заказчиков — разные учётные записи и разные экраны входа. Сотрудники входят с подтверждением TOTP; с этапа 2 системы лицензирования — через корпоративный каталог (OIDC или LDAP).

## 8. Архитектура

### 8.1. Стек

| Слой | Технология |
|---|---|
| Сервер | Python 3.13, Django 5.2 LTS, DRF, drf-spectacular |
| БД | PostgreSQL 17 |
| Очередь и кэш | Celery 5, Redis 7 |
| Интерфейс | Vue 3, TypeScript, Vite, PrimeVue, Pinia, Vue Router, vue-i18n — те же версии и правила, что в консоли системы лицензирования |
| Документы | Шаблоны DOCX (`docxtpl`) → PDF в отдельном контейнере сервиса документов |
| Шлюз | Nginx |
| Наблюдаемость | Структурные журналы, `/health`, метрики Prometheus |

| Компонент | Назначение |
|---|---|
| `lk-api` | REST API кабинета и администрирования |

## 10. Миграция данных

### 10.1. Соответствие

| ЛК 2.0 (MariaDB) | ЛК 3.0 (PostgreSQL) | Правило |
|---|---|---|
| `Clients` | `Organization` | ИНН из `ExternalCode`; `legacy_client_code` сохраняется |
| `Cabinet` | `ClientUser` | Хэш пароля переносится как есть с `password_scheme = legacy_sha512`; `AccessGranted = false` → неактивен |
| `RegData` | `License` + `LicenseKey` | Серийный номер, код (шифруется), артикул, `Total` → количество; срок рассчитывается по полю `FF`; `Archived`, `Hidden` сохраняются |
| `RegData.Used` | — | Не переносится; остаток приходит из системы лицензирования; используется для сверки |
| `Licensing` | — (в систему лицензирования) | Активации `os_node`, `instance_id` = UUID v5 от `SystemUniqueNumber` |
| `OutgoingMail` | `OutgoingMail` | Переносится за последние 12 месяцев |
| Администраторы | `StaffUser` | Создаются заново с TOTP |

### 10.2. Порядок

| Шаг | Действие | Критерий |
|---|---|---|
| 1 | Скрипт миграции `lk-migrate` читает MariaDB, пишет PostgreSQL; идемпотентен | Повторный запуск не создаёт дублей |
| 2 | Пробная миграция на копии продуктивной БД | Отчёт: количество записей по таблицам совпадает; ошибки разобраны |
| 3 | Передача лицензий в систему лицензирования через Integration API и активаций — скриптом миграции legacy | Сверка: число лицензий и сумма количеств совпадают; `used` совпадает с `RegData.Used` или расхождение объяснено |
| 4 | Опытная эксплуатация ЛК 3.0 на копии с тестовой группой сотрудников и 3–5 заказчиками | Нет блокирующих замечаний |
| 5 | Переключение: ЛК 2.0 только чтение, финальная миграция изменений, перевод DNS и маршрутов `/api/activate/` | Окно до 2 ч в нерабочее время |
| 6 | ЛК 2.0 хранится в режиме только чтения 3 месяца, затем выводится | Решение владельца ЛК |

### 10.3. Откат

До шага 5 откат не требуется. После переключения в течение 7 дней возможен возврат на ЛК 2.0: изменения, сделанные в ЛК 3.0, выгружаются отчётом и вносятся вручную. Маршрут `/api/activate/` при откате остаётся на системе лицензирования.

## 11. Требования к совместимости

1. Форматы серийного номера и кода не меняются; ранее выданные ключи действуют.
2. Пользователи кабинета входят со старыми паролями.
3. Адреса `lk.alter-os.ru`, `/activate`, `/api/activate/` сохраняются; последние два обслуживает система лицензирования.
4. Шаблоны сертификатов и писем переносятся с сохранением внешнего вида.
5. Выгрузка XLSX при выпуске сохраняет состав колонок ЛК 2.0 — она используется системой лицензирования на этапе 1 (документ 2, раздел 14.1) до включения Integration API.

## 14. Приёмка

| № | Критерий | Проверка |
|---|---|---|
| 1 | Все функции ЛК 2.0 из раздела 3.1 доступны в ЛК 3.0, кроме активации, перенесённой в систему лицензирования | Матрица соответствия |
| 2 | Генерация серийных номеров и кодов совпадает с ЛК 2.0 на всех эталонных примерах | Автотест |
| 3 | Пробная миграция: количество записей совпадает; клиенты входят со старыми паролями | Протокол миграции |
| 4 | Выпуск, продление и отзыв доходят до системы лицензирования не позже 1 мин; при недоступности — доставляются после восстановления | Тест интеграции с отказом |
