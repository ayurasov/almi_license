| Параметр | Значение |
|---|---|
| Документ | Правила разработки с ИИ-ассистентами (документ 6 комплекта) |
| Версия | 1.0 |
| Дата | 14.10.2026 |
| Статус | Проект; утверждает технический лидер |
| Связанные документы | 1 — Архитектура (разделы 14, 17); 3 — Бэклог; 7 — Стенды и CI/CD |

## 1. Назначение

Этап 1 делается быстро за счёт генерации кода ИИ-ассистентами (Cursor, Claude Code, Copilot и аналогичные). Скорость полезна, только если сгенерированный код не нарушает контракты, модульные границы и безопасность. Документ задаёт эти рамки: что ассистент получает на вход, чего ему делать нельзя, как формулируется задача, как проверяется результат.

Правила обязательны для всех участников и для всех ассистентов. Раздел 3 — готовое содержимое файла `AGENTS.md` в корне репозитория; ассистенты читают его автоматически.

## 2. Принципы

1. **Контракт прежде кода.** Ассистент реализует то, что описано в `contracts/` и документах 1–2. Он не придумывает поля, коды ошибок и форматы.
2. **Тест прежде реализации.** Сначала тест по контракту и векторам, затем код, который его проходит.
3. **Малые изменения.** Одна задача — один сценарий или один экран, изменение до 400 строк без учёта тестов и сгенерированного кода.
4. **Человек отвечает за слияние.** Ассистент не сливает изменения сам. Автор запроса на слияние понимает каждую строку.
5. **Критичные модули — только с ревью технического лидера** (раздел 8).
6. **Ограничители в CI сильнее договорённостей.** То, что можно проверить автоматически, проверяется автоматически.

## 3. Содержимое `AGENTS.md`

```markdown
# AGENTS.md — правила для ИИ-ассистентов и разработчиков

## Проект
Система лицензирования АЛМИ: сервер (Django), веб-консоль (Vue 3), модуль DL (C++).
Один образ работает в режимах DEPLOYMENT_MODE=central и DEPLOYMENT_MODE=local.
Источник истины — каталог contracts/ и документы docs/specs/01-architecture.md, docs/specs/02-interaction-spec.md.

## Стек и версии
- Python 3.13, Django 5.2 LTS, DRF 3.15, drf-spectacular, PostgreSQL 17, psycopg 3
- Vue 3.5, TypeScript 5 (strict), Vite 6, PrimeVue 4, Pinia, Vue Router 4, vue-i18n
- C++17, CMake 3.28, libsodium, libcurl, nlohmann/json, GoogleTest
- Тесты: pytest, hypothesis, vitest, Playwright, ctest, k6
- Не добавлять зависимости без согласования с техническим лидером (файл docs/dependencies.md).

## Команды
- make up — поднять окружение; make seed — тестовые данные
- make test — все тесты; make test-server; make test-console; make test-dl
- make lint — ruff, mypy, eslint, vue-tsc, clang-tidy
- make contract-check — сверка OpenAPI реализации с contracts/openapi-product-api-v1.yaml
- make vectors — прогон эталонных векторов на сервере и в DL
Перед тем как сообщить о завершении задачи, выполни make lint и make test для затронутых частей.

## Структура
server/apps/<модуль>/  domain/ (сервисы и правила), models.py, api/ (сериализаторы, представления), tests/
Модули: catalog, licensing, activation, policy, packages, signing, stats, audit, iam, outbox,
api_product, api_admin, api_sync, compat.
console/src/  views/, components/, stores/, api/ (сгенерирован из OpenAPI, руками не правится), i18n/
sdk/cpp/  include/license_module.h (публичный ABI), src/, tests/

## Жёсткие правила
1. Не изменять contracts/ — только по задаче с меткой contract и с ревью технического лидера.
2. Бизнес-логика только в domain/ модулей. Представления и сериализаторы ничего не решают.
3. Модуль не читает и не пишет таблицы другого модуля; только через его domain-сервис (проверяет import-linter).
4. Время только через infra.clock.Clock; datetime.now() и time.time() в коде запрещены.
5. PolicyEngine — чистая функция: без БД, сети, времени системы, случайности.
6. Изменение мест, лицензий и активаций — только в транзакции с select_for_update на строке лицензии.
7. Каждое изменение прав пишет событие аудита через audit.domain.record().
8. Секреты только из переменных окружения и Docker secrets. Никаких ключей, паролей, токенов в коде, тестах, фикстурах, журналах.
9. В журналы не попадают: полный ключ лицензии, аренда, подпись, nonce, хэши компонентов отпечатка, пароли.
10. Ошибки API — только application/problem+json с кодом из каталога docs/specs/02-interaction-spec.md раздел 16. Новые коды не придумывать.
11. Ответы Product API — только добавляющие изменения; поля не удаляются и не переименовываются.
12. Криптография только через infra.crypto.CryptoProvider (сервер) и crypto/ (DL). Не писать свою криптографию, не использовать random для секретов.
13. Миграции БД — обратимые; изменение существующих колонок — в два шага (добавить, перенести, удалить в следующем выпуске).
14. Консоль: компоненты PrimeVue, тексты только через i18n, клиент API только сгенерированный, состояние в Pinia.
15. C ABI (license_module.h) — только добавление функций и значений в конец перечислений.

## Как выполнять задачу
1. Прочитай задачу, ссылки на разделы docs/ и файлы contracts/.
2. Напиши тесты по критериям приёмки. Запусти — они должны падать.
3. Реализуй минимальный код, который проходит тесты.
4. Запусти make lint и make test. Исправь всё.
5. Обнови docs/ и CHANGELOG.md, если меняется поведение.
6. Опиши в запросе на слияние: что сделано, как проверено, что осталось, какие решения принял сам.
Если контракт неясен или противоречив — остановись и задай вопрос, не угадывай.

## Модули с обязательным ревью технического лидера
signing, infra/crypto, activation (учёт мест), policy, api_product/auth (подпись запросов),
packages (импорт и выпуск), audit, iam, compat (разбор входных данных),
sdk/cpp: LeaseVerifier, Transport, SecureStore, StateEvaluator, RollbackGuard, TrialTracker, OfflineFiles.
```

## 4. Соглашения по коду

### 4.1. Python

| Правило | Значение |
|---|---|
| Форматирование и линтер | `ruff format`, `ruff check` (правила E, F, I, B, UP, S, SIM, DJ) |
| Типы | `mypy --strict` для `domain/` и `infra/`; аннотации везде |
| Слои | `api/` → `domain/` → `models` / `infra/`; обратные импорты запрещены |
| Доменные сервисы | Функции или классы без состояния; на вход — значения и `Clock`, на выход — результат или доменное исключение |
| Исключения | Доменные исключения в `domain/errors.py`; отображение в `code` RFC 9457 — в одном месте `api_product/errors.py` |
| Транзакции | `transaction.atomic()` на уровне доменного сервиса, не представления |
| Идентификаторы | ULID с префиксом (`act_`, `srv_`) для внешних, UUID для внутренних |
| Тесты | `pytest`, фабрики `factory_boy`, без обращения к сети; property-тесты для политики и учёта мест |
| Покрытие | `activation`, `policy`, `signing` — не ниже 85 %; остальные — не ниже 70 % |

### 4.2. TypeScript и Vue

| Правило | Значение |
|---|---|
| Режим | `strict: true`, `noUncheckedIndexedAccess: true` |
| Компоненты | `<script setup lang="ts">`, Composition API; без Options API |
| UI | PrimeVue; свои компоненты — только в `components/` при повторном использовании |
| Данные | Клиент из OpenAPI (`openapi-typescript` + `openapi-fetch`), запросы в Pinia-хранилищах |
| Тексты | Только `vue-i18n`, ключи `<экран>.<элемент>` |
| Формы | Валидация по схеме (`zod`), ошибки сервера отображаются по полям |
| Тесты | `vitest` для хранилищ и логики, Playwright для сценариев |
| Эталон | Экран «Заказчики» (E07-03 бэклога): новый экран генерируется по нему |

### 4.3. C++

| Правило | Значение |
|---|---|
| Стандарт | C++17, без исключений через границу ABI; коды `LM_Result` |
| Форматирование | `clang-format` (Google, ширина 110) |
| Анализ | `clang-tidy` (bugprone, cert, cppcoreguidelines, modernize), ASan и UBSan в CI на Linux |
| Память | RAII, без голых `new`/`delete`; секреты обнуляются `sodium_memzero` |
| Платформенный код | Только в `src/platform/{win,linux}`; общий код без `#ifdef` |
| Потоки | Публичные функции потокобезопасны; внутреннее состояние под одним мьютексом |
| Тесты | GoogleTest; эталонные векторы из `contracts/vectors` обязательны |

## 5. Шаблон задачи для ассистента

Задача в трекере и запрос к ассистенту оформляются одинаково. Пример для истории E03-05:

```markdown
## Задача E03-05. Освобождение места POST /api/v1/activations/{id}/release

Контекст
- docs/02 раздел 5.4; contracts/openapi-product-api-v1.yaml, operationId=release
- Модуль: server/apps/activation; представление: server/apps/api_product

Критерии приёмки
1. Активная активация → статус released, ответ 200 по схеме ReleaseResponse с квитанцией JWS.
2. Повторный вызов с тем же Idempotency-Key → тот же ответ, без повторной записи в аудит.
3. Чужая подпись → 401 signature_invalid.
4. Несуществующая активация → 404 activation_not_found.
5. Событие аудита activation.released с причиной.

Ограничения
- Не менять contracts/. Не менять другие модули, кроме activation и api_product.
- Время через Clock. Изменение в транзакции с блокировкой строки лицензии.

Порядок
1. Тесты в server/apps/activation/tests/test_release.py и server/apps/api_product/tests/test_release_api.py.
2. Реализация activation.domain.release().
3. make lint && make test-server && make contract-check.

Результат: запрос на слияние в ветку stage1, описание по шаблону.
```

## 6. Ветки, коммиты, слияние

| Правило | Значение |
|---|---|
| Основная ветка | `main` — только выпущенный код; защищена |
| Ветка этапа | `stage1` — рабочая ветка этапа 1; защищена, слияние через запрос с зелёным CI |
| Ветки задач | `feat/E03-05-release`, `fix/E03-05-…`, `docs/…`, `contract/…` |
| Коммиты | Порционные, по одному логическому шагу (тест, реализация, документация); формат Conventional Commits: `feat(activation): release endpoint (E03-05)` |
| Слияние в `stage1` | Squash; минимум один ревьюер; для модулей раздела 8 — технический лидер |
| Слияние `stage1` → `main` | Только после readiness gate этапа (раздел 15.7 документа 1); тег `v1.0.0` |
| Исправления после выпуска | Ветка `hotfix/…` от `main`, слияние в `main` и `stage1` |
| CODEOWNERS | `contracts/`, `server/apps/signing/`, `server/infra/crypto/`, `server/apps/policy/`, `sdk/cpp/src/crypto/` → технический лидер |

## 7. Готовность задачи

### 7.1. Готова к работе

- [ ] Есть ссылка на историю бэклога и разделы документов 1–2.
- [ ] Критерии приёмки проверяемы.
- [ ] Указаны модули, которые можно менять.
- [ ] Зависимости закрыты или есть заглушки.
- [ ] Для модулей раздела 8 назначен ревьюер.

### 7.2. Выполнена

- [ ] Все критерии приёмки покрыты автотестами и проходят.
- [ ] `make lint`, `make test`, `make contract-check`, `make vectors` — зелёные.
- [ ] Нет новых зависимостей без согласования.
- [ ] Нет секретов, отладочного кода, закомментированного кода.
- [ ] Обновлены документация и `CHANGELOG.md`.
- [ ] Ревью пройдено; замечания закрыты.
- [ ] Изменение влито в `stage1`, стенд `test-central` обновлён.

## 8. Ревью критичных модулей

Технический лидер проверяет по чек-листу; каждый пункт отмечается в запросе на слияние.

| Область | Что проверяется |
|---|---|
| Криптография | Только `CryptoProvider`; алгоритм и `kid` из конфигурации; проверка подписи до разбора полезной нагрузки; сравнение в постоянное время; нет самописных примитивов |
| Подпись запросов | Строка подписи строго по разделу 4.4 документа 2; окно времени; хранение `nonce`; тело хэшируется в байтах, а не после разбора JSON |
| Учёт мест | `select_for_update` на лицензии; проверка лимита и запись в одной транзакции; тест на параллельные запросы |
| Политика | Чистота функции; все векторы; границы дат и часовых поясов; `null`-значения |
| Разбор файлов и входа | Ограничение размера до разбора; проверка подписи до доверия содержимому; отказ на неизвестной версии формата |
| Хранение секретов | Нет секретов в журналах, исключениях, ответах API, дампах; ключ выпуска только из Docker secret |
| DL | Проверка цепочки до корня; монотонность `seq`; обработка отказа хранилища без падения продукта; обнуление секретов |

## 9. Что запрещено ассистенту

1. Изменять `contracts/`, `AGENTS.md`, CI-конфигурацию, `CODEOWNERS` без задачи с соответствующей меткой.
2. Отключать или ослаблять тесты, линтеры, правила `import-linter`, чтобы пройти CI.
3. Добавлять зависимости, сетевые вызовы в тестах, обращения к внешним сервисам.
4. Генерировать ключи, пароли, токены в коде или фикстурах; использовать продуктивные данные заказчиков.
5. Передавать в ассистента продуктивные данные, ключи, выгрузки ЛК с реальными заказчиками. Для разработки — только обезличенные данные стенда.
6. Принимать решения по архитектуре: новые модули, таблицы, форматы, коды ошибок — только через ADR.

## 10. Работа с данными и ассистентами

| Данные | Можно передавать ассистенту |
|---|---|
| Код репозитория, документы 1–7, контракты | Да |
| Обезличенные фикстуры и тестовые векторы | Да |
| Тестовые ключи стенда (`test-root`) | Да, только открытые части |
| Выгрузка ЛК с реальными заказчиками | Нет |
| Продуктивные ключи, аренды, журналы | Нет |
| Ключи и пароли любых стендов | Нет |

Если ассистент работает в облаке, используется корпоративная учётная запись с отключённым обучением на данных. Для модулей криптографии допускается генерация каркаса и тестов; итоговый код пишет или переписывает разработчик.

## 12. Метрики процесса

| Метрика | Цель этапа 1 | Где смотреть |
|---|---|---|
| Время от открытия до слияния запроса | до 1 рабочего дня | Трекер репозитория |
| Доля запросов, возвращённых на доработку после ревью ТЛ | до 30 % | Трекер репозитория |
| Дефекты, найденные на E2E, по модулям раздела 8 | 0 блокирующих | Протокол E2E |
| Покрытие критичных модулей | 85 % сервер, 90 % DL | Отчёт CI |
| Красный CI в `stage1` | не дольше 2 ч | CI |
