## 1. Назначение

Документ раскладывает этап 1 (6 недель) на эпики и пользовательские истории с критериями приёмки, исполнителями, оценками и зависимостями. Каждая история — законченный кусок работы, который можно передать разработчику или ИИ-ассистенту как задачу и проверить за 30–60 минут ревью.

Бэклог переносится в трекер задач один к одному: эпик — эпик, история — задача, критерии приёмки — чек-лист задачи.

## 2. Правила бэклога

### 2.1. Обозначения

| Обозначение | Значение |
|---|---|
| `FS` | Full-stack разработчик Python/Vue (в команде двое: `FS1` — сервер, `FS2` — консоль и сервер) |
| `CPP` | Разработчик C++ (модуль DL) |
| `PD` | Разработчик АльтерОфис Desktop (со стороны продукта) |
| `QA` | Инженер по тестированию |
| `DO` | DevOps-инженер |
| `TL` | Технический лидер / архитектор |
| `PO` | Владелец продукта со стороны АЛМИ |
| Оценка | Идеальные человеко-дни с учётом генерации кода ИИ-ассистентом |
| Ревью ТЛ | `да` — обязательное ручное ревью технического лидера (раздел 17 документа 1) |
| Приоритет | `M` — обязательно для выпуска; `S` — желательно, переносится на этап 2 без ущерба для выпуска |

### 2.2. Готовность истории к работе

История берётся в работу, если: есть ссылка на раздел документа 1 или 2 и на контракт в `contracts/`; критерии приёмки проверяемы; зависимости закрыты или имеют заглушки; для истории с `Ревью ТЛ = да` назначен ревьюер.

### 2.3. Готовность истории к закрытию

История закрыта, если: все критерии приёмки выполнены и покрыты автотестами; CI зелёный (линтеры, типы, тесты, сверка контракта, import-linter, сканирование секретов); выполнено ревью (для критичных модулей — ТЛ); обновлены документация и `CHANGELOG.md`; изменение влито в рабочую ветку этапа (раздел 6 документа 6).

### 2.4. Формат критериев

Критерии записаны кратко, в форме «условие → результат». Номера ошибок и полей — по документу 2.

- **Full-stack перегружены на 20 % (около 10 чел.-дн.).** Нужен третий full-stack разработчик на недели 2–5 с загрузкой 50 % (консоль: E07-04…E07-09, E10-01, E10-02) либо перенос части историй раздела 7 на этап 2. Без этого неделя 6 уходит на доработку, а не на стабилизацию.
- **DevOps на границе ёмкости.** На недели 4–6 загрузка DevOps повышается до 60 %.
- Технический лидер и QA имеют резерв, который уходит на ревью, исправление дефектов и повторные E2E.

## 6. Критический путь

1. E00-02 → E00-04 → E02-03 → E13-02: эталонные векторы до кода; без них сервер и модуль расходятся.
2. E01-01 → E03-01 → E03-04 → E09-04: модель данных и ядро активации — основа локального сервера.
3. E13-01…E13-10 → E14-02…E14-07 → E16-04: модуль должен быть готов к началу недели 4, иначе интеграция в продукт уходит за релиз. Заглушка E13-11 позволяет команде продукта начать раньше.
4. E00-09 → E11-01, E11-03: без реальных запросов Nextcloud и `registration.sh` адаптеры делаются вслепую.
5. E17-04 → выпуск: церемония ключей и встраивание продуктивного ключа в сборку продукта согласуются с графиком выпуска продукта заранее.

## 7. Перенос на этап 2 при нехватке времени

Если на неделе 4 отставание больше 3 дней, в указанном порядке переносятся: капча портала офлайн-активации (E08-02 — оставить только лимит частоты), выгрузка журнала аудита в CSV (E10-04), предупреждение о сроке пакетов (E12-04), тёмная тема консоли (E07-01). Критерии приёмки 15.6 документа 1 при этом не меняются.
