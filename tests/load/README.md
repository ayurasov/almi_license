# Нагрузка этапа 1 (E16-05, промпт I5-02)

| Сценарий | Нагрузка | Цель |
|---|---|---|
| `check` | 100 запросов/с, 15 мин | p95 < 500 мс, ошибки < 0,1 % |
| `activate` | 20 запросов/с, 10 мин | p95 < 500 мс |
| `race` | 200 пользователей одновременно активируют одну лицензию с limit = 100 | активных активаций ровно 100 + резерв (3 % → 103) |

## Запуск

- `make load-smoke` — те же шаги в малом масштабе (минута) на этом хосте. Запускается в CI, задача `load-smoke`, отчёт — артефакт.
- `make load` — полный масштаб: набор `seed-load` (20 000 лицензий, 500 000 активаций, 10 000 устройств с ключами). Только на нагрузочном стенде с параметрами `staging` (вопрос 28).

`tests/load/stand.sh` поднимает сервер на новой БД `almi_load`: 2 процесса uvicorn, пул соединений, лимиты частоты выключены. Затем `run.sh` по шагам:
1. `manage.py seed_load` создаёт данные. Команда работает только при `SEED_LOAD_ALLOWED`, в `prod` она запрещена.
2. `sign.py` заранее подписывает запросы ключами устройств. `created` каждого запроса равен секунде, в которую k6 его отправит, `nonce` у каждого свой.
3. k6 (`grafana/k6:2.3.0` в docker) выполняет сценарии `scenario.js`.
4. Проверяется результат гонки, собираются `/metrics` сервера и топ-10 запросов `pg_stat_statements`. Для последнего нужно расширение `pg_stat_statements` на сервере БД; в CI его нет.
5. Пишется отчёт `report.md`.

Файлы с закрытыми ключами устройств и ключами лицензий удаляются в конце прогона. Хранить их можно только на стенде.

## Узкие места, найденные на smoke

1. **Соединения с БД.** Под ASGI у каждого одновременного запроса свой поток и своё соединение. 200 одновременных активаций превысили `max_connections`: 99 ответов 500, и гонка дала 101 вместо 103. Исправлено пулом psycopg (`DATABASE_POOL_MAX_SIZE`; в комплекте локального сервера 10 на процесс): запросы ждут свободное соединение.
2. **Активации одной лицензии выполняются последовательно.** Так задумано: `select_for_update` на строке лицензии, правило 6. При 200 одновременных запросах p95 около 4,5 с. Цель гонки — отсутствие двойного списания, она достигнута. Если для крупных заказчиков понадобится ускорение, есть варианты: сократить работу под блокировкой (подписывать аренду после фиксации места) или разделить лимит на сегменты. Код сервера в этой истории не менялся, кроме пула.
