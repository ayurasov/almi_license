# Промпты для разработки этапа 1

Документ — рабочий сценарий выполнения этапа 1 силами разработчиков с ИИ-ассистентами. Он содержит:

- порядок итерационной разработки: что делается в каждой итерации, в какой последовательности и как проверяется;
- шаблоны промптов для каждого шага работы над историей;
- готовые промпты для ключевых историй бэклога (документ 3) по всем потокам: сервер, консоль, модуль DL, тестирование, DevOps;
- контрольные промпты для завершения итерации и этапа.

Промпты рассчитаны на агентов, работающих в репозитории (Cursor, Claude Code, Copilot Workspace и аналогичные), и на чат-модели для ревью. Текст промптов — на русском; имена в коде, коммитах и API — на английском.

## Итерационная модель

### 2.1. Уровни

| Уровень | Длительность | Результат | Проверка |
|---|---|---|---|
| Этап | 6 недель | Выпуск системы лицензирования | Readiness gate (раздел 15.7 документа 1) |
| Итерация | 1 неделя (I1–I6) + подготовка I0 | Работающий прирост на стенде `test-central` | Демонстрация и контрольный промпт итерации |
| История | 0,25–2 дня | Слитый запрос в `stage1` | Критерии приёмки, CI, ревью |
| Шаг | 30–120 минут | Коммит | Тесты шага зелёные |

Правило: каждая итерация заканчивается работающей системой. Ничего не копится «до интеграции в конце» — на стенде всегда последняя слитая версия, и сквозной сценарий прошлой итерации продолжает проходить.

### 2.2. Цикл истории

```
P0 старт сессии → P1 план → P2 тесты (красные) → P3 реализация (зелёные)
   → P4 самопроверка → P5 исправление CI → P6 независимое ревью
   → [P7 ревью критичного модуля] → P8 документация → P9 закрытие
```

| Шаг | Кто | Что получается | Коммит |
|---|---|---|---|
| P0 | Разработчик → ассистент | Ассистент загрузил контекст и подтвердил понимание | — |
| P1 | Ассистент, утверждает разработчик | План: файлы, тесты, риски, вопросы | — |
| P2 | Ассистент | Тесты по критериям приёмки; падают | `test(<модуль>): … (Exx-yy)` |
| P3 | Ассистент | Минимальная реализация; тесты проходят | `feat(<модуль>): … (Exx-yy)` |
| P4 | Ассистент | Отчёт о соответствии критериям и правилам `AGENTS.md` | при необходимости `refactor` |
| P5 | Ассистент | Зелёный CI | `fix(…)` |
| P6 | Другая сессия ассистента | Список замечаний | — |
| P7 | Технический лидер с ассистентом | Чек-лист раздела 8 документа 6 | — |
| P8 | Ассистент | Документация, `CHANGELOG.md` | `docs(…)` |
| P9 | Ассистент | Запись в журнале прогресса, описание запроса на слияние | — |

### 2.3. Правила сессий

1. **Одна история — одна ветка — одна сессия.** Новая история начинается в новой сессии с промпта P0. Длинные сессии теряют контекст и начинают противоречить ранним решениям.
2. **Новая сессия при переполнении.** Если ассистент начал забывать ограничения, повторять исправленные ошибки или контекст занят больше чем на 70 %, сессия закрывается промптом P9 (частичное закрытие) и продолжается новой с P0.
3. **Реализация и ревью — разные сессии.** Сессия, которая писала код, не делает его независимое ревью (P6).
4. **Разработчик утверждает план.** Ассистент не пишет код, пока разработчик не ответил «план утверждён» на P1.
5. **Остановка при неясности.** Если контракт неясен или противоречив, ассистент останавливается и формулирует вопрос (P12). Ответ фиксируется в ADR или в журнале решений, а не только в чате.
6. **Коммит на каждый зелёный шаг.** Не накапливать несколько шагов в одном коммите; порционные коммиты в ветку задачи, squash при слиянии в `stage1`.
7. **Контракты неприкосновенны.** Изменение `contracts/` — только отдельной историей с меткой `contract` и ревью технического лидера.

### 2.4. Память проекта в репозитории

Ассистент не помнит прошлых сессий. Память хранится в файлах, которые он читает в P0:

| Файл | Содержимое | Кто обновляет |
|---|---|---|
| `AGENTS.md` | Правила и команды (документ 6, раздел 3) | Технический лидер |
| `docs/progress/stage1.md` | Журнал: закрытые истории, текущая итерация, открытые вопросы | Ассистент в P9, разработчик проверяет |
| `docs/progress/iteration-N.md` | План и итог итерации N | Технический лидер в начале и конце итерации |
| `docs/decisions.md` | Мелкие решения, принятые в историях (что не тянет на ADR) | Ассистент в P9 |
| `docs/adr/` | Архитектурные решения | Технический лидер |
| `docs/specs/` | Документы 1–9 комплекта в Markdown | Технический лидер |

Документы комплекта кладутся в `docs/specs/` в начале I0 с короткими именами: `01-architecture.md`, `02-interaction-spec.md`, `03-backlog.md`, `04-catalog.md`, `05-messages.md`, `06-ai-rules.md`, `07-environments.md`, `08-lk-tz.md`. Контракт Product API лежит в `contracts/openapi-product-api-v1.yaml`. Промпты ниже ссылаются на эти пути.

## Признаки проблем и реакция

| Признак | Что означает | Реакция |
|---|---|---|
| Ассистент меняет тесты, чтобы они прошли | Подгонка под реализацию | Откатить; повторить P3 с явным запретом менять тесты |
| Ассистент «исправляет» эталонный вектор | Ошибка в коде или в векторе | P12; решение — только технический лидер |
| В diff файлы вне плана | Расползание задачи | Отклонить; разбить историю |
| Одинаковая логика в двух модулях | Нарушение «один доменный сервис» | Вынести в domain нужного модуля; добавить правило import-linter |
| Растёт число `# type: ignore`, `noqa`, `skip` | Технический долг | Проверка в P10; лимит — 0 новых без ссылки на историю |
| Ассистент придумывает поле или код ошибки | Контракт не прочитан | Вернуться к P0; проверить, что контракт был в контексте |
| Красный CI в `stage1` дольше 2 ч | Блокировка всех потоков | Откат последнего слияния; исправление в ветке |
| Итерация закрыта меньше чем на 80 % | Переоценка ёмкости | P10; перенос историй с приоритетом `S` по разделу 7 документа 3 |
